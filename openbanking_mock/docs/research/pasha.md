## 3. Auth / headers / environments
- Security scheme `Bearer` = `apiKey` in header `Authorization` ("Please Enter Authentication Token"); no operation declares `security`.
- Declared headers (all of them): `Consent-ID` (required on all AIS data calls - accounts, card-accounts, cards, loans, savings - 21 ops; optional on 19 payment ops) and `API-ContractID` (optional on 17 ops). **No `X-Request-ID`, `Digest`, `x-jws-signature`, `PSU-*`, `TPP-*` headers appear anywhere in the spec** (they exist in the Georgian standard; the spec simply omits them).
- Portal text (SpecificDoc): TPP identification by QWAC only - valid, issued by an eIDAS QTSP, not revoked, else connection closed with HTTP 403; any number of certificates per TPP while CA and organizationIdentifier stay the same. SCA: only "Redirect OAuth 2.0 workflow" (app-to-app, decoupled, embedded = not supported). Max `frequencyPerDay` 4; SCA validity 90 days; consent establishment timeout 3 days; `withBalance` supported; account identifiers IBAN + maskedPan (no BBAN); consent presets `availableAccounts=allAccounts`, `availableAccountsWithBalances=allAccounts` (no `allPsd2`); multicurrency aggregation + sub-account levels; balance types closingBooked, expected, openingBooked, interimAvailable, interimBooked (no forwardAvailable); transaction params dateFrom/dateTo/entryReferenceFrom (no deltaList); transaction fields debtorName, remittanceInformationUnstructuredArray, balanceAfterTransaction (no instructionIdentification, structured remittance, creditorAgent, debtorAgent); no signing baskets; card-accounts endpoints supported; "Support of Standing orders endpoint: no"; owner name display supported; multilevel SCA supported; "Amounts are returned as float type values"; transactions appear with delay; accounts described by product name + ISO20022 code (CACC); consents "for all accounts or a given set of IBANs only". Conformity statement: "BerlinGroup ... Implementation Guidelines version 1.3".
- Environments (Getting Started page): sandbox `https://psd2-xs2a-sandbox.pashabank.ge/`, demo user `demo` / password `demo` / OTP `1234` (not used). Production base URL, OIDC/authorize/token endpoints and certificate-enrolment details are NOT published (Cert page `/Cert` generates test certificates - form, not used). The spec's own `servers` are the generic AltaSoft hosts `psd2-sandbox1.altasoft.ge` and `psd2-sandbox2.altasoft2.ge` (no scheme).
- Georgian-language: portal has a Georgian toggle (`?culture=ka-GE`, label "ქარ"); Georgian text appears inside the spec descriptions (e.g. "c - პირობითი" = conditional); no English manual of the Georgian standard is reachable (v0.6 EN link 404).

## 4. Schema highlights & deviations
- Not stock Berlin Group: AltaSoft model. `CreateConsentRequestBody` required = `access, consentType, frequencyPerDay, recurringIndicator`; optional `validTo` (date; "9999-12-31" = max; NOT `validUntil`); no `combinedServiceIndicator`. `consentType` enum `global | detailed | aspspManaged | accountList`. `access` = object with arrays `payments, cards, cardAccounts, savings, loans, securities` of `AccountAccessRights` whose `AccessRightsCode` enum = `ais, accountDetails, balances, transactions, orders, ownerName, psuName, psuLeanIdentification, trustedBeneficiaries, initiatePayments, fundsConfirmations, userParameters, ibanChecks, corporateParameters, accountCheckParameters`. `consentStatus` enum adds `replacedByTpp`. Response `CreateConsentResponse{consentStatus, consentId, scaMethods, chosenScaMethod, challengeData, _links, psuMessage}`.
- `AccountDetails` required = `currency, iban, other, resourceId` (both `iban` and `other: GenericAccountIdentification`), plus `ownerName`, `ownerNames[{name, role: owner|legalRepresentative|authorisedUser|co-borrower|co-signer}]`, `name`, `displayName`, `product`, `cashAccountType` (ISO ExternalCashAccountType1Code), `status` (`enabled|deleted|blocked`), `bic`, `usage` (`PRIV|ORGA`), `details`, `balances`, `tariffs`, `interest`, `relatedDates`, `collateralsInvolved`, `guaranteeInvolved`, `_links`. `AccountReference` uses `typeCode`/`typeProprietary`/`other`/`proxy` (not `cashAccountType`).
- `BalanceType` = closingBooked, expected, openingBooked, interimAvailable, interimBooked, forwardAvailable, nonInvoiced, information. `BookingStatus` = booked, pending, both, information, all. `TransactionStatus` = ACCC ACCP ACSC ACSP ACTC ACWC ACWP RCVD PDNG RJCT CANC ACFC PATC PART (same as Georgian guide). `ScaStatus` = received, psuIdentified, psuAuthenticated, scaMethodSelected, started, unconfirmed, finalised, failed, exempted. `AuthenticationType` = SMS_OTP, CHIP_OTP, PHOTO_OTP, PUSH_OTP, SMTP_OTP. `ChargeBearer` = CRED, DEBT, SHAR, SLEV (no `OUR`); `PriorityCode` = NORM, HIGH; `FrequencyCode` = Daily, Weekly, EveryTwoWeeks, Monthly, EveryTwoMonths, Quarterly, SemiAnnual, Annual, MonthlyVariable; `ExecutionRule` following|preceding.
- Payment bodies are ISO-20022-like nested objects (not flat BG fields): `SinglePaymentInitiationRequest{paymentIdentification{endToEndId, instructionId, uetr}, instructedAmount{currency, amount}, creditorAccount, creditorAgent, intermediaryAgent1/2, creditor, chargeBearer, chargesAccount, remittanceInformationUnstructured[] (ARRAY of Max140Text), remittanceInformationStructured[], additionalInformation, instructionPriority, ultimateDebtor, debtor, debtorAccount, requestedExecutionDate}`. Response `PaymentInitiationRequestResponse{paymentId, transactionStatus (required), transactionFees, currencyConversionFee, estimatedTotalAmount, estimatedInterbankSettlementAmount, scaMethods, chosenScaMethod, challengeData, _links, psuMessage, apiClientMessages}`.
- Errors: HTTP 400/401/403/404/405/406/408/409/415/429/500/503, body RFC 7807 style `{type,title,status,detail,instance,code,additionalErrors[],_links}` with per-status `code` enums: 400 {FORMAT_ERROR, PARAMETER_NOT_CONSISTENT, PARAMETER_NOT_SUPPORTED, SERVICE_INVALID, RESOURCE_UNKNOWN, RESOURCE_EXPIRED, RESOURCE_BLOCKED, TIMESTAMP_INVALID, PERIOD_INVALID, SCA_METHOD_UNKNOWN, SCA_INVALID, CONSENT_UNKNOWN, SESSIONS_NOT_SUPPORTED, PAYMENT_FAILED, EXECUTION_DATE_INVALID, DUPLICATE_REQUEST_UID, CONSENT_TYPE_NOT_SUPPORTED}; 401 {CERTIFICATE_*, ROLE_INVALID, SIGNATURE_INVALID/MISSING, CORPORATE_ID_INVALID, PSU_CREDENTIALS_INVALID, CONSENT_INVALID, CONSENT_EXPIRED, TOKEN_UNKNOWN/INVALID/EXPIRED, REQUIRED_KID_MISSING}; 403 {CONSENT_UNKNOWN, SERVICE_BLOCKED, RESOURCE_UNKNOWN, RESOURCE_EXPIRED, PRODUCT_INVALID}; 404 {RESOURCE_UNKNOWN, PRODUCT_UNKNOWN}; 405 {SERVICE_INVALID, CANCELLATION_INVALID}; 406 REQUESTED_FORMATS_INVALID; 408 REQUEST_TIMEOUT; 409 STATUS_INVALID; 415 UNSUPPORTED_MEDIA_TYPE; 429 ACCESS_EXCEEDED. 2xx warnings in `apiClientMessages[{category,code:WARNING,path,text}]`.
- Pagination: no page/limit params; only `entryReferenceFrom`, `dateFrom/dateTo`, `deltaList`, undocumented `state`, and `_links` in `GetTransactionListResponse`/`AccountReport` (`first/next/previous/last` hrefs not typed beyond `HrefType`). Limits quoted on the portal (freq 4/day, SCA 90 d, consent timeout 3 d) are not in the YAML.
- The spec is example-rich (2,121 `example(s)` nodes) and the examples ARE Georgian: IBAN `GE02AL0000000000118060`, currency `GEL`, BIC `ALTAGE22`, `resourceId` UUIDs, `_links.href` like `v2/accounts/<uuid>/balances`. Good seed data for a mock.
- Georgian-language bits inside descriptions: "c - პირობითი" (conditional), "m - სავალდებულო", "o - არასავალდებულო" annotations on payment fields.

## TRAPS for a schema-validated mock built from this spec (highest priority first)
1. **String types are modelled as objects.** 20 schemas are `type: object` with a single read-only integer property `length` (a .NET Swashbuckle artefact): `AnyBICIdentifier, BBANIdentifier, BICFIIdentifier, CountryCode, CurrencyCode, ExternalFinancialInstitutionIdentification1Code, IbanIdentifier, LEIIdentifier, Max1000Text, Max1024Text, Max140Text, Max16Text, Max2048Text, Max2Text, Max35Text, Max4Text, Max500Text, Max70Text, PhoneNumber, StrAmount` (their real constraints - pattern/minLength/maxLength - live only in the free-text `description`, e.g. `pattern: [A-Z]{3,3}`, `pattern: -?[0-9]{1,14}(\.[0-9]{1,3})?`). `ISODate` / `ISODateTime` are `type: object` with no properties (System.DateOnly / System.DateTime). A real response such as `{"currency":"GEL","amount":"12.50"}` FAILS validation against the file as published (the spec's own examples, e.g. `"currency":"GEL"`, contradict its schemas). PATCH: replace each of these 22 schemas by `{type: string, [pattern|minLength|maxLength]}` (`ISODate` -> `format: date`, `ISODateTime` -> `format: date-time`) before loading into any validator. (If `StrAmount` should be a JSON number - see next point - use `oneOf: [string pattern, number]`.)
2. **Amount type conflict:** spec description says string (`pattern -?[0-9]{1,14}(\.[0-9]{1,3})?`), SpecificDoc says "Amounts are returned as float type values". Accept both in the mock.
3. **Over-strict `required` lists (nullable-reference-type artefact):** `SinglePaymentInitiationRequest` requires 17 fields incl. `intermediaryAgent1`, `intermediaryAgent2`, `chargesAccount`, both remittance forms, `ultimateDebtor`, `additionalInformation`; `PeriodicPaymentInitiationRequest` 23; `RecurringPaymentRequest` 19; `BulkPaymentInitiationRequest` 16; `AccountDetails` requires `other` and `iban` together. Verbatim validation rejects normal requests - relax to the fields the Georgian guide marks mandatory (`instructedAmount`, `creditorAccount`, plus per-product rules).
4. **No JWS/Digest/X-Request-ID/PSU-IP-Address in the spec** although the Georgian standard (and the OB Home banks) require them; the portal itself only talks about QWAC mTLS.
5. **`servers` unusable** (no scheme, generic AltaSoft hosts). Real sandbox host `psd2-xs2a-sandbox.pashabank.ge`, path prefix presumably the spec paths as-is (`/v2/...`) - unverified.
6. **Docs vs spec disagree:** SpecificDoc claims IG 1.3 and no standing orders / only Redirect OAuth, but the spec is v2.0 with `periodic-payments`, loans, savings, cards and `/openfinance/v2/*`. Treat the spec as the superset, SpecificDoc as the PASHA subset of what is actually enabled (unverified).
7. Security declared as `apiKey`/`Authorization` and not attached to any operation => validators will treat every endpoint as unauthenticated.
8. Berlin Group payment-service/product naming differs from the OB Home banks (concrete `/payments/aspsp` here vs `{payment-service}/{payment-product}` there) - a mock covering both families needs two routers.
